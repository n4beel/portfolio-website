Async control flow in Node · taxonomy from Node.js Design Patterns ch. 4–5 · examples my own

One installer, three eras

I rewrote the same dependency installer eleven times. The work never changes: read a manifest, fetch the package, follow its dependencies. Only two things vary: the shape the work takes on the timeline, and the syntax you spell that shape in. Three shapes × three syntaxes is the whole problem.

the question

Same fetches. Three totals.

Press Run. All three lanes install the root package, then fetch every dependency it declares, identical work, identical registry speeds. The only difference is when each fetch is allowed to start. Add dependencies with the first slider and watch one lane grow while another doesn't; change the concurrency limit and watch the third lane slide between the two.

The law behind the picture: sequential total is the sum of the durations; parallel total is the max; queued lands in between, and never puts more than concurrency requests in flight. Push the concurrency slider to 1 and the third lane becomes the first; push it past the dependency count and it becomes the second.

Keep this trace in mind for the rest of the page. Nothing below changes it. Promises and async/await rewrite how you spell these three lanes: they don't add a fourth one, and they don't make any lane faster.

the primitive everything is built from one shape

A callback is a "what to do next", handed forward

Before any of the patterns make sense, one idea has to be solid. A synchronous function returns its result. An asynchronous function can't: the result doesn't exist yet. So instead of returning, it takes the rest of your program as an argument and calls it later. That argument is the continuation.

Everything so far, the pyramid, the recursion, the counter, is a workaround for one fact: the call stack unwinds before your result arrives. Any ordering you want after that point, you have to reconstruct by hand. the whole of era one in one sentence

v1 callbacks/01-nested · callback hell

Version 1 installs exactly one package, and it's already unreadable

No dependency walking here yet, no loop, no concurrency. Just four operations that must happen in order: check the store, fetch the package, make the directory, write the tarball. Four steps. And because each one is asynchronous, each one nests inside the previous one's callback.

inStore(storePath, …)Already in the store? Then we're done: call back and stop.
get(spec, …)Fetch it from the registry. Slow, and off the stack.
mkdirp(dirname(storePath), …)Create the folder tree before writing into it.
writeFile(storePath, content, …)Save the tarball.
cb(null, storePath, true)Only now does the caller learn anything happened.

Written with an if/else for every error, those four steps produce this. The bars on the left are indentation depth. The shape is the whole point:

Why it's called "hell": the error handling for step 1 (if (err)) and the success path for step 1 (else) end up separated by every other step in the program. To find out what happens when inStore() fails, your eye travels 25 lines. The closing }) }) }) }) tail carries no information at all, yet you have to count it to know where you are.

Not a performance problem

The pyramid runs perfectly well. Callback hell is a readability failure, and readability failures become correctness failures: a forgotten return before cb(err) means the callback fires twice, and at depth 8 nobody notices.

The fix isn't a library: it's discipline

Version callbacks/02-flattened changes no behaviour whatsoever. It applies three rules and the pyramid collapses:

  1. Return early. return cb(err) instead of if/else: the error path exits, so the happy path never gets indented.
  2. Name your continuations. The mkdir → writeFile pair becomes a top-level writeToStore(); get → writeToStore becomes fetchPackage().
  3. Reuse them. Those named functions are now callable from anywhere, which is exactly what v2 and v3 will need.
callbacks/02-flattened/install.js: same work, depth 3 instead of 9function writeToStore(storePath, content, cb) { mkdirp(dirname(storePath), err => { if (err) { return cb(err) } writeFile(storePath, content, cb) }) } function fetchPackage(spec, storePath, cb) { get(spec, (err, content) => { if (err) { return cb(err) } writeToStore(storePath, content, err => { if (err) { return cb(err) } cb(null, content) }) }) }

Note writeFile(storePath, content, cb) on the last line of writeToStore: the callback is passed straight through rather than wrapped in another arrow. Every avoided wrapper is an avoided level.

the turn from one package to a whole tree

Now do it for every dependency, recursively

v2 and v3 add one requirement: after writing a package to the store, read its manifest and install each of its dependencies too, down to maxDepth. Both versions share identical code for this, the same fetchPackage, the same install, the same guard clauses:

shared by callbacks/03-sequential and callbacks/04-parallelexport function install(spec, maxDepth, cb) { const storePath = storePathFor(spec) inStore(storePath, (err, alreadyInstalled) => { if (err) { return cb(err) } if (alreadyInstalled) { // in the store already: read its manifest and follow its deps return readManifest(storePath, (err, manifest) => { if (err) { return cb(err) } return installDeps(manifest, maxDepth, cb) }) } fetchPackage(spec, storePath, (err, manifest) => { if (err) { return cb(err) } if (manifest.dependencies) { return installDeps(manifest, maxDepth, cb) } return cb() // a leaf package: nothing to follow }) }) }

The entire difference between the two versions lives inside installDeps. Twelve lines, in one file, in one function. Everything else is byte-for-byte the same.

Why process.nextTick(cb) guards the early exits

When maxDepth === 0 or a package has no dependencies, installDeps has nothing async to wait for, so calling cb() directly would fire it synchronously, before the caller had finished setting itself up. That's Zalgo: a function that is sometimes sync and sometimes async. process.nextTick defers the call to the next iteration of the event loop, so the API is always asynchronous.

v2 callbacks/03-sequential · one at a time

Sequential: recursion, because a for loop can't wait

The instinct is to write for (const dep of deps) install(dep, …) and expect each iteration to wait. It won't: install() returns immediately, so the loop would fire all of them at once. A loop counter lives on the stack, and the stack is gone by the time the callbacks run.

So the counter has to live somewhere that survives: an argument to a function that calls itself from inside the callback.

callbacks/03-sequential/install.js: the whole differencefunction installDeps(manifest, maxDepth, cb) { if (maxDepth === 0) { return process.nextTick(cb) } const deps = getDependencies(manifest) if (deps.length === 0) { return process.nextTick(cb) } function iterate(index) { if (index === deps.length) { return cb() } // ← base case: all done install(deps[index], maxDepth - 1, err => { if (err) { return cb(err) } iterate(index + 1) // ← the "loop", one frame deeper }) } iterate(0) }

Read it as a cycle, not a stack

iterate(0)Is 0 the end? No. Launch install(deps[0]) and return immediately. The stack empties. Node is idle, waiting on the network.
…dep 0 finishes…Its callback fires. Inside it: iterate(1). Only now does dep 1 start.
…dep 1 finishes…iterate(2). And so on. At any moment exactly one request is in flight.
iterate(deps.length) → cb()The index hits the end. The single base case fires the caller's callback. Exactly once.

Where does "done" come from? From the index reaching deps.length. There is one exit, it's a plain equality check, and it cannot fire early. That simplicity is what you're buying by giving up the speed.

The traversal order is depth-first

Because install() for dep 0 fully completes, including its own recursive installDeps, before dep 1 starts, the install walks the tree exactly the way npm ls prints it, top to bottom:

1react 2├── loose-envify 3│ ├── js-tokens 4│ └── object-assign 5├── scheduler 6│ └── picocolors 7└── prop-types

One package at a time, one order, fully deterministic. Run it twice and the console output is identical, which is exactly the property a lockfile wants.

Doesn't the recursion blow the stack?

No, and this is the part that trips people up. iterate(index + 1) is called from inside a callback, which the event loop invokes on a fresh, empty stack. The previous iterate frame is long gone. It looks like recursion in the source but behaves like a loop at runtime. (Contrast with a directly recursive sync function, which really would grow the stack.)

v3 callbacks/04-parallel · unlimited parallel execution

Parallel: launch them all, then count the finishes

If you don't need the ordering, the for loop that failed before becomes exactly right. Fire every install() in one synchronous pass; every request goes out before Node returns to the event loop. Now the problem inverts: not "when do I start the next one?" but "how do I know they've all finished?"

callbacks/04-parallel/install.js: same 12 lines, rewrittenfunction installDeps(manifest, maxDepth, cb) { if (maxDepth === 0) { return process.nextTick(cb) } const deps = getDependencies(manifest) if (deps.length === 0) { return process.nextTick(cb) } let completed = 0 let hasErrors = false function done(err) { if (err) { hasErrors = true return cb(err) } if (++completed === deps.length && !hasErrors) { return cb() } } for (const dep of deps) { install(dep, maxDepth - 1, done) // same callback for every one } }

Three things carry the whole pattern:

  • One shared callback. Every install() gets the same done function, closing over the same completed variable. That closure is the only thing holding the group together.
  • ++completed === deps.length is the join. Whichever task finishes last is the one that trips the condition and calls cb(). You don't know which task that will be, and it doesn't matter.
  • hasErrors is a latch, not a counter. On failure cb(err) fires immediately, but the other requests are still in flight and will still call done. The flag stops those late arrivals from firing cb() a second time.

Compare the two exits. Sequential has one base case that can only be reached one way. Parallel has a counter that N different callbacks race to increment, plus a flag guarding against double-calling. The extra bookkeeping is the price of the speed.

The traversal order is now a wavefront

Every sibling starts together and each subtree races independently, so completion order is whatever the registry decides:

1react 2├── loose-envify ← all three start 3│ ├── js-tokens ← these start the moment loose-envify lands 3│ └── object-assign 2├── scheduler ← in the same tick as loose-envify 3│ └── picocolors 2└── prop-types ← in the same tick as loose-envify

The badges are depth, not order, because there is no order. Run it twice and the log lines come out shuffled.

v3·1 callbacks/05-deduped · the race condition

Going parallel invented a bug that couldn't exist before

Dependency graphs are graphs, not trees: that is the whole reason lockfiles exist. Both react and react-dom depend on loose-envify. In v2 that was harmless: the first install('loose-envify') ran to completion, so by the time the second one called inStore() the package was already there and it returned early.

In v3 they both start in the same tick. Watch the interleaving:

t=0 A install('loose-envify') → inStore(…) … async, off the stack t=0 B install('loose-envify') → inStore(…) … async, off the stack nothing has been written yet: the package genuinely is not in the store t=1 A ← false → fetchPackage() ✗ fetches t=1 B ← false → fetchPackage() ✗ fetches again

Two registry requests, two writes to the same store path, and that package's own dependencies get installed twice, which then doubles again one level down. With a circular dependency this doesn't just waste bandwidth, it never terminates: a depends on b depends on a, and each visit looks new because the check always loses the race.

The general shape: check-then-act across an await point

inStore() and writeFile() are two separate asynchronous operations, so between them the event loop is free to run anybody else's code. Any "look before you leap" that spans an async boundary is a race waiting to happen. It isn't specific to files: the same shape bites you with database upserts, cache fills, and lock acquisition.

The fix is a synchronous claim

You can't make the check-and-write atomic, so instead you record the intent the moment it's formed, in memory, synchronously, before yielding to the event loop:

callbacks/05-deduped/install.js: the only change from v3const installing = new Set() export function install(spec, maxDepth, cb) { if (installing.has(spec)) { return process.nextTick(cb) // someone else already claimed it } installing.add(spec) const storePath = storePathFor(spec) inStore(storePath, (err, alreadyInstalled) => { // …byte-for-byte identical to v3 from here down

The has / add pair runs in one uninterrupted synchronous block: no callback, no await, no chance for another task to slip between them. That's the whole trick: the guard must not be asynchronous.

  • The Set is not a cache. It tracks "someone has started on this package", not "this package is finished". A duplicate caller returns immediately without waiting for the first one, which is fine for an installer that only cares the package lands in the store eventually.
  • process.nextTick(cb), again. Same Zalgo defence as before: the early exit is on a synchronous code path, so the callback has to be deferred to stay asynchronous, or the parent's completed counter could be incremented before the loop that's counting it has finished.
  • It's process-local. Two Node processes installing into the same store would still race. Real deduplication across processes needs a lock or an atomic filesystem operation.
the bill the second thing parallel broke

Unbounded concurrency is a denial-of-service you wrote yourself

The race is fixed, but v3 still has no ceiling, and "launch them all" recurses. A package with 100 dependencies, whose dependencies have 100 each, puts 10,000 registry requests in flight before the first one comes back:

depth 0 1 request depth 1 100 requests ← all fired in one tick depth 2 10,000 requests ← fired as each depth-1 manifest lands

What actually happens: EMFILE from exhausting file descriptors, ECONNRESET as the registry rate-limits you, memory ballooning with buffered tarballs, or you get your CI runner's IP throttled for everyone. The sequential version could never do this. It was capped at 1 by construction, and that cap was the one good thing about it.

So the missing piece is a ceiling you choose, not 1, not ∞, but n. The chapter builds it in three steps before applying it to the install:

callbacks/limited-inline.js

The pattern, inline

The parallel counter plus two more variables: running and nextTaskIndex. A next() function starts tasks while running < concurrency, and each completion calls next() again.

callbacks/task-queue.js

Extracted to a class

Same logic as TaskQueue, but the task list becomes a mutable queue you can pushTask() into at any time, including from inside a running task.

callbacks/task-queue-events.js

Given events

extends EventEmitter. Errors become an 'error' event and "the queue drained" becomes an 'empty' event, so completion no longer has to travel back through callbacks.

v4 callbacks/06-queued · limited concurrency

Version 4 deletes the callback plumbing entirely

This is the version worth studying twice, because the change isn't "add a queue in front of the same code". The signature changes, and that changes everything downstream:

callbacks/06-queued/install.jsexport function install(spec, maxDepth, cb) export function install(spec, maxDepth, queue) // install() no longer reports completion. At all. export function install(spec, maxDepth, queue) { if (installing.has(spec)) { return } // ← no cb, so nothing to defer installing.add(spec) queue.pushTask(done => { installTask(spec, maxDepth, queue, done) }) }

With no callback to fire, the process.nextTick guards vanish: there's no Zalgo risk in a function that never calls anyone back. And installDeps loses all of its bookkeeping:

The move: a task is done when its own page is saved

Look closely at installTask. It calls installDeps(...) and then cb() on the very next line. It does not wait for the children:

callbacks/06-queued/install.js: installTaskfetchPackage(spec, storePath, (err, manifest) => { if (err) { return cb(err) } if (manifest.dependencies) { installDeps(manifest, maxDepth, queue) return cb() // ← children are now separate queued tasks, not my problem } return cb() })

In v3 the install was a tree of nested callbacks: the root's callback couldn't fire until every descendant's callback had. In v4 it's a flat pool of sibling tasks that happen to enqueue more siblings. Nobody waits for anybody.

So how does anyone find out it finished?

They subscribe. Completion stopped being a value threaded through callbacks and became an event on a shared object:

callbacks/06-queued/install-cli.jsconst installQueue = new TaskQueue(concurrency) installQueue.on('error', console.error) installQueue.on('empty', () => console.log('Install complete')) install(spec, maxDepth, installQueue) // no callback anywhere

Note the error handling change too. In v3 the first failure called cb(err) and aborted that whole subtree. Here a failed task emits 'error', gets logged, and the install carries on: one unpublished package no longer kills the run. That's usually what you want from an installer, but it is a real behavioural difference, not just a refactor.

Inside the queue

Forty lines, and only three pieces of state, concurrency, running, and the pending array:

callbacks/task-queue.jsexport class TaskQueue extends EventEmitter { constructor(concurrency) { super() this.concurrency = concurrency this.running = 0 this.queue = [] } pushTask(task) { this.queue.push(task) process.nextTick(this.next.bind(this)) return this // chainable: .pushTask(a).pushTask(b) } next() { if (this.running === 0 && this.queue.length === 0) { return this.emit('empty') } while (this.running < this.concurrency && this.queue.length > 0) { const task = this.queue.shift() task(err => { if (err) { this.emit('error', err) } this.running-- process.nextTick(this.next.bind(this)) // a slot opened: refill it }) this.running++ } } }
  • The while loop is the throttle. It starts tasks until either the slots are full or the queue is dry: that single condition is the entire difference between v3 and v4.
  • running++ comes after task(...). That looks like a bug and isn't: if the task happens to call its callback synchronously, running-- would run before running++ and the counter would go negative. Ordering it this way keeps the arithmetic correct either way.
  • process.nextTick before next(). It lets the current synchronous block finish: a task pushing three subtasks gets all three into the queue before the scheduler looks again, and it prevents next() recursing into itself and growing the stack.
  • 'empty' can fire more than once across a long-running queue: it means "nothing running, nothing pending right now". For the install that's exactly the finish line, because tasks are only ever enqueued by other tasks.

recall the callback era

What to keep from the callback era

  • Callback hell is about indentation, not speed. Early returns and named functions fix it without changing a single behaviour.
  • Sequential = start the next one inside the previous callback. The loop variable becomes a function parameter, because parameters survive the stack unwinding and local variables don't.
  • Parallel = start them all, count the finishes. The shared closure variable is the entire coordination mechanism.
  • "Done" is the thing you design. Sequential gets it free from a base case; parallel builds it from a counter and defends it with a flag; the queue owns it outright and announces it.
  • Concurrency creates races that sequential code cannot have. Any check-then-act spanning an async boundary needs a synchronous claim: v3's installing Set, recorded before you yield.
  • Unlimited parallelism is a bug the moment recursion is involved. The useful number is almost never 1 or ∞; it's n, and TaskQueue is how you spell it.
  • Queuing changes the architecture, not just the pace. Once completion is an event, install() stops taking a callback, stops counting children, and stops caring who called it. Decoupling is the real payoff: the throttle is almost a side effect.
  • Count the bookkeeping, not the lines. Of the ~40 lines you just read, roughly half exist only to answer "did it fail?" and "are we there yet?": if (err) return cb(err), completed, hasErrors, process.nextTick. Hold that number. The next era is about deleting it.
Era two

Promises: the same three shapes, with the bookkeeping built in

A promise is a callback turned inside out. Instead of you handing a continuation into a function, the function hands you back an object you can attach continuations to. That inversion is small, but it lets the language, rather than your code, own three things the callback era made you write by hand.

Error propagation

A rejection travels down the chain on its own. Every if (err) { return cb(err) } from the callback era becomes nothing at all, plus one .catch() at the very end.

Guaranteed asynchrony

.then() always defers to the microtask queue, even on an already-resolved promise. Zalgo is impossible, so every process.nextTick(cb) guard is deleted.

Settle-once semantics

A promise resolves or rejects exactly once, forever. The double-callback bug, and the hasErrors latch that defended against it, cannot occur.

The bridge: promisify

The install's utils.js is the only file that really had to change between chapters. Every callback-based function got wrapped:

promises/promisify.js: the adapter, in nine linesfunction promisify(callbackBasedFn) { return function promisifiedFn(...args) { return new Promise((resolve, reject) => { const newArgs = [...args, (err, result) => { if (err) { return reject(err) } resolve(result) }] callbackBasedFn(...newArgs) }) } }

The error-first convention maps one-to-one onto reject/resolve, which is why a mechanical wrapper works at all. In practice you use util.promisify, or, better, the promise-native APIs directly: node:fs/promises instead of node:fs, and fetch unwrapped.

The shapes are unchanged: verify it against the trace

Everything below produces exactly the timelines at the top of this page. If you find yourself thinking "promises made it faster", check which lane you're actually in. Promise.all isn't fast because it's a promise; it's fast because it starts everything before awaiting anything.

p·v2 promises/01-sequential · one at a time

The for loop comes back, because now it isn't launching anything

The callback era needed iterate(index) because a loop couldn't wait. Here the loop returns, and it works. The trick is that it isn't starting tasks at all. It's assembling a chain, synchronously, in a single pass:

promises/01-sequential/install.jsfunction installDeps(manifest, maxDepth) { let promise = Promise.resolve() // the seed if (maxDepth === 0) { return promise } const deps = getDependencies(manifest) for (const dep of deps) { promise = promise.then(() => install(dep, maxDepth - 1)) } return promise }

Read the loop body as an accumulator, exactly like reduce: each pass replaces promise with a longer chain. The loop finishes in microseconds, before a single byte has been fetched. What it leaves behind is a linked list of "and then do this".

iteration 0 promise = P₀ iteration 1 promise = P₀.then(→ install(loose-envify)) = P₁ iteration 2 promise = P₁.then(→ install(prop-types)) = P₂ iteration 3 promise = P₂.then(→ install(scheduler)) = P₃ ↑ each dep can only start once the previous one has settled return P₃ // settles when the last dep in the chain does

One subtlety in writeToStore

writeFile resolves with undefined, so the chain would lose the manifest. Hence the extra step: .then(() => manifest), a deliberate hop whose only job is to put the value back into the pipeline. Returning a value from a .then callback is how you pass data forward; returning a promise is how you wait for it first.

p·v3 promises/02-parallel · unlimited parallel

Parallel is two lines, because Promise.all is the counter and the latch

A promise is not a task you can start. It is a task that has already started, and a handle for finding out how it went. That's why map is parallel and then is sequential, and why "lazy promise" needs a whole custom class to exist. the mental model that makes everything else obvious

The rest of the family

Promise.all: all must succeed, rejects on the first failure. Promise.allSettled: waits for every one and reports each outcome; the right choice when one unpublished package shouldn't sink the whole install. Promise.race: first to settle, win or lose; good for timeouts. Promise.any: first to succeed, rejecting only if all fail. Note that none of them cancel the losers: every request still runs to completion.

p·v4 promises/03-queued · limited concurrency

The queue keeps its job, and loses its callback

The TaskQueue from the callback era needed each task to accept a done callback and promise to call it. Now a task just returns a promise, and the queue reads completion off it directly:

  • .finally() is exactly the right verb. "Free the slot whichever way this went" is a single concept, and it now reads as one. In the callback version that logic had to be duplicated mentally across the error and success paths of every task.
  • .catch() before .finally() matters. The catch handles the rejection and returns a fulfilled promise, so finally runs on a settled chain and the rejection never escapes as an unhandled promise rejection.
  • this.next() is called directly now: no process.nextTick wrapper. .finally() callbacks already run as microtasks, so the deferral the callback era had to add by hand is now free.
  • pushTask still uses process.nextTick, though, and that's what lets install-cli.js push the root task before attaching its 'empty' listener without missing the event.

Where the dedupe check moved

The callback era's installing guard sat at the top of install(). Here it sits in installDeps, one step earlier, the package is claimed before it's ever enqueued:

promises/03-queued/install.jsfunction installDeps(manifest, maxDepth, queue) { if (maxDepth === 0) { return } const deps = getDependencies(manifest) for (const dep of deps) { if (!installing.has(dep)) { queue.pushTask(() => install(dep, maxDepth - 1, queue)) installing.add(dep) } } } // returns undefined: fire and forget

Same principle as the callback era: has and add are both synchronous, in the same uninterrupted block, so no second caller can slip between them. And note the lazy arrow again: () => install(…), because the queue must decide when the task runs. Passing install(dep, …) directly would start every request instantly and defeat the whole queue.

Worth noticing: the root package isn't claimed

In the callback era's v4, install() itself did installing.add(spec), so every package including the root was registered. Here the CLI pushes the root directly with queue.pushTask(() => install(spec, maxDepth, queue)) and the guard only runs over deps. A page linking back to the root will therefore enqueue it a second time. It's harmless: the package is now in the store, so the second pass just reads its manifest and finds every dependency already claimed, but it is a real asymmetry between the two versions, not a simplification.

Era three

Async/await: the loop the callback era couldn't write

Everything so far has been a workaround for one fact: the call stack unwinds before your result arrives. An async function is the language finally fixing that directly: at every await the function suspends, its stack frame is preserved, and it resumes into that same frame when the promise settles.

Which means a loop variable can live on the stack again. The callback era's iterate(index) recursion and the promise era's promise = promise.then(…) accumulator both collapse into the thing you wanted to write in the first place:

async-await/01-sequential/install.js: sequential, in fullasync function installDeps(manifest, maxDepth) { if (maxDepth === 0) { return } const deps = getDependencies(manifest) for (const dep of deps) { await install(dep, maxDepth - 1) } }

Three lines of body. Compare the three eras of exactly this function:

The pyramid, finally flat

The bigger win is in install() itself. The callback era's version branched: already in the store read it and install, otherwise fetchPackage it and install, so the call to installDeps appeared twice, at the bottom of two separate nested callbacks. With await, both branches just assign to a local variable and fall through to one shared ending:

async-await/01-sequential/install.jsexport async function install(spec, maxDepth) { const storePath = storePathFor(spec) let content if (!(await inStore(storePath))) { content = await fetchPackage(spec, storePath) // not in the store: fetch it } if (!manifest.dependencies) { return } // a leaf package if (!manifest) { manifest = await readManifest(storePath) // was in the store: load it } return installDeps(manifest, maxDepth) }

Maximum nesting depth: one. Against the version this page opened with: depth nine, with a five-line tail of closing brackets. That is the entire argument for the new syntax in a single screenshot. Read top to bottom, it's just a description of the algorithm.

Errors become ordinary

Because await throws on rejection, a single try/catch now covers both synchronous throws and asynchronous failures, and the CLI can use top-level await, no wrapper function at all:

async-await/01-sequential/install-cli.jstry { await install(spec, maxDepth) // top-level await, in an ES module console.log('Downloaded complete') } catch (err) { console.error(err) process.exit(1) }
a·v3 async-await/02-parallel · unlimited parallel

Async/await gives you sequencing. It does not give you concurrency.

This is where most real-world async code goes wrong, so it's worth stating flatly: await inside a loop is the sequential pattern. It is not a slower parallel: it is a different lane on the trace at the top of this page. To go parallel you still need Promise.all, and the v3 file proves it by being byte-identical to the promise version:

async-await/02-parallel/install.js: identical to promises/02-parallelasync function installDeps(manifest, maxDepth) { if (maxDepth === 0) { return } const deps = getDependencies(manifest) const promises = deps.map(dep => install(dep, maxDepth - 1)) return Promise.all(promises) }

The async keyword on that function now buys nothing: there's no await in the body. It's kept for signature consistency; deleting it would behave the same.

The mistake, side by side

The rule that catches it every time: ask where the function calls happen relative to the await. If install() is invoked after an await that depends on the previous iteration, you are sequential. If every invocation happens before any awaiting, you are parallel.

a·v4 async-await/03-queued · limited concurrency

Turning the event back into something you can await

The queue is unchanged from p·v4: task().catch().finally(), same three fields. Two details differ, and both are worth the detour.

1. Not everything needs to be async

async-await/03-queued/install.jsfunction installDeps(manifest, maxDepth, queue) { // ← no `async` if (maxDepth === 0) { return } const deps = getDependencies(manifest) for (const dep of deps) { if (!installing.has(dep)) { queue.pushTask(() => install(dep, maxDepth - 1, queue)) installing.add(dep) } } }

It enqueues and returns. There is nothing to await, so marking it async would only wrap undefined in a promise and imply a completion signal that doesn't exist. The async keyword is a claim about your return value: don't make it idly.

2. await once(queue, 'empty')

The CLI closes the loop between the three eras. Completion left the callback in era one and became an event; here the event becomes a promise again, so the program can be read straight down:

async-await/03-queued/install-cli.jsimport { once } from 'node:events' const queue = new TaskQueue(concurrency) queue.pushTask(() => install(spec, maxDepth, queue)) queue.on('taskError', console.error) await once(queue, 'empty') console.log('Install complete')

Why 'error' had to be renamed to 'taskError'

Two separate special cases collide here. First, EventEmitter treats 'error' specially: emitting it with no listener attached throws. Second, and this is the one that bites, events.once() also attaches its own 'error' listener, and will reject the promise you're awaiting if that event fires. So with an 'error'-named event, a single failed fetchPackage would reject await once(queue, 'empty') and crash the CLI instead of just logging a dead dep. Renaming the event sidesteps both behaviours. It's a one-word change that only makes sense once you know both rules.

Note also that pushTask is called before the listeners are attached, and it still works, because pushTask defers next() with process.nextTick, so the current synchronous block finishes (registering both listeners) before the queue can possibly emit anything. The Zalgo discipline from era one is still quietly holding the design together.

traps the failure modes the new syntax introduces

Three ways the new syntax bites back

Promises remove whole categories of bug, and add a few of their own. All three of these are in the chapter's example folders, and all three are the kind you ship without noticing.

1. return vs return await inside try

Outside a try/catch the two are equivalent, which is why linters used to flag return await as redundant. Inside one, they do completely different things.

2. Recursion that leaked nothing with callbacks leaks memory here

The callback era made a point of it: iterate(index + 1) inside a callback doesn't grow the stack, because the event loop invokes callbacks on a fresh one. Recursion was free. With promises it isn't: returning the recursive call chains the promises together, and a chain that never ends can never be garbage collected:

The same trap exists in async form: return leakingLoopAsync() at the end of an async function chains identically. And here the third era wins outright, because it can express an unbounded loop with no recursion at all:

traps/recursion-leak.js: the version with no trade-offasync function nonLeakingLoopAsync() { while (true) { await delay(1) console.log(`Tick ${Date.now()}`) } }

One frame, reused forever. No chain accumulates, and errors still propagate normally, which is exactly what the callback-era workaround (a manual internalLoop() wrapped in new Promise, rejecting on error) had to build by hand.

3. A promise starts the moment it is created

There is no such thing as a promise you have made but not started. const p = fetch(spec) has already sent the request; await only decides when you look at the result. That's why the queue and the sequential chain both take () => install(…) rather than install(…), and why a genuinely lazy promise needs a custom LazyPromise subclass to defer the executor until someone calls .then. If you want a task you can hold and start later, the thing you need is a function that returns a promise, not a promise.

All three eras · in one page

What to keep

  • Three shapes, three syntaxes, nine cells. The matrix at the top of this page is the whole of it. Every async control flow you write is one of those cells or a composition of them.
  • The shape decides the runtime; the syntax decides the readability. Rewriting a sequential install in async/await makes it shorter, not faster. Only moving from one column of the matrix to another changes the trace.
  • Promises delete the bookkeeping, not the thinking. Error propagation, guaranteed asynchrony, and settle-once semantics come free, so if (err) return cb(err), process.nextTick(cb), and hasErrors all vanish. Deciding how many things run at once is still your job, in every era.
  • then is lazy, map is eager. That single distinction is the difference between sequential and parallel in promise-land, and the reason a queue must be handed () => task() and never task().
  • await in a loop is sequential. If you meant to fan out, start everything first and await the collection. It never throws and never logs: it shows up only as a latency number nobody can explain.
  • Concurrency creates races. Any check-then-act spanning an async boundary needs a synchronous claim before you yield: the installing Set survives unchanged through all three eras because the hazard is structural, not syntactic.
  • Unlimited is not a concurrency setting. The useful answer is almost never 1 or ∞. Every era ends at the same place: a TaskQueue with a number in it.
  • Recursion changed cost between eras. Free in callbacks, a memory leak in promises, unnecessary in async/await, where a plain while loop finally does the job.

The installer is the same program in every one of these files. What eleven rewrites actually teach is that you have three vocabularies for saying the same three things, and that picking the right shape matters more than picking the newest syntax. eleven rewrites, one idea
